Qué acaba de pasar

El navegador no toca las tablas. Las once están cerradas con row level security y sin ninguna política, que es la forma de decir «no pasa nadie».

Lo único que puede hacer esta página es pedirle a la base que ejecute tres funciones: una para listar las mesas, otra para guardar la reserva y otra para leer la lista. La de guardar comprueba antes que el nombre tenga sentido, que la fecha no haya pasado y que las personas quepan en la mesa.

Y por eso la clave puede ser pública

La clave publishable viaja en el navegador de todo el mundo. Con ella no se puede leer un teléfono entero, ni borrar una reserva, ni ver los pedidos: solo se pueden hacer esas tres cosas.

Una regla de negocio, tres capas de defensa

Una regla de negocio expresa cómo debe funcionar el restaurante. Por ejemplo: «una mesa no puede tener dos reservas para la misma fecha y hora». Esa frase no es todavía código. Para que se cumpla, la aplicamos en más de un lugar, y cada capa tiene un trabajo distinto.

1. El frontend guía, pero no decide la verdad

El frontend es esta página: los campos, los botones y los mensajes que ves antes de enviar. Aquí se revisa lo obvio para no hacer perder un viaje al servidor:

  • los campos obligatorios no se pueden dejar vacíos;
  • la hora se propone entre 11:00 y 22:00;
  • el número de personas empieza en 1;
  • si eliges una mesa de 2 puestos y pides para 4, la página te avisa antes de enviar.

¿Por qué no basta?

Alguien puede modificar el navegador, construir otra página o llamar a la API sin pasar por estos campos. Por eso una comprobación de frontend mejora la experiencia, pero no protege la base.

2. La función de la base aplica la regla al recibir la solicitud

Cuando pulsas Enviar la reserva, el navegador no ejecuta un INSERT directo. Pide a la función registrar_reserva() que valide y guarde. La función vive dentro de PostgreSQL, de modo que las mismas reglas se aplican aunque la llamada no venga de este formulario.

ReglaQué comprueba la función
Datos razonablesNombre de 3 a 100 caracteres, teléfono válido y al menos una persona.
Fecha y horaFecha de hoy a 90 días y horario de 11:00 a 22:00.
Mesa posibleLa mesa existe y tiene puestos suficientes.
Sin choqueNo hay otra reserva para esa misma mesa, fecha y hora.

Si alguna condición falla, la función lanza un error y PostgreSQL revierte la operación: no queda una reserva a medias ni un cliente de prueba.

3. Las restricciones de tabla defienden la estructura

Una restricción de base de datos está declarada en la propia tabla. No depende de esta página ni de una persona que recuerde validar. El motor la aplica a cada INSERT o UPDATE.

RestricciónEjemplo en Restaurante ABCQué evita
NOT NULLUna reserva necesita fecha, hora, cliente y mesa.Reservas incompletas.
CHECKpersonas > 0 y puestos > 0.Reservar para cero personas o crear una mesa sin capacidad.
Clave foráneareserva.cliente_id y reserva.mesa_id.Una reserva que apunte a un cliente o mesa inexistente.
UNIQUELa combinación mesa, fecha y hora.Dos reservas idénticas incluso si dos navegadores envían al mismo tiempo.

En esta demostración la función ya rechaza nuevos choques. La restricción UNIQUE es la segunda barrera estructural que se activa cuando no existan reservas duplicadas heredadas.

La secuencia completa

  1. El formulario orienta y detecta errores sencillos.
  2. La función vuelve a comprobar las reglas de negocio y decide si guarda.
  3. Las restricciones de la tabla impiden que los datos imposibles entren, incluso ante llamadas simultáneas.

Idea clave

Frontend: «esto parece incorrecto; corrígelo antes de enviar».
Base de datos: «aunque intentes enviarlo por otro camino, no se guarda».

¿Y si usáramos Beekeeper Studio?

Beekeeper es un cliente de PostgreSQL: permite conectarse y escribir SQL. No vuelve una conexión segura por sí solo. La seguridad la decide el rol de PostgreSQL con el que se abre la conexión. Por eso no se entrega la contraseña de postgres a quien solo necesita registrar una reserva.

El patrón recomendado: permiso para una sola puerta

En vez de conceder INSERT libre sobre las tablas, el docente podría crear un rol de uso limitado, por ejemplo reserva_escritura. Ese rol no tendría permiso para consultar ni modificar directamente cliente, reserva ni las otras tablas. Solo podría ejecutar la función controlada registrar_reserva().

-- Esto lo prepara el docente en el SQL Editor, una sola vez.
CREATE ROLE reserva_escritura LOGIN NOINHERIT PASSWORD 'una-clave-secreta';
GRANT USAGE ON SCHEMA public TO reserva_escritura;
GRANT EXECUTE ON FUNCTION public.registrar_reserva(
  TEXT, TEXT, DATE, TIME, INTEGER, INTEGER
) TO reserva_escritura;

-- Sin GRANT sobre tablas ni secuencias: no puede hacer INSERT directo.
-- La contraseña no va en el HTML, Git ni el chat de la clase.

Así, la palabra SELECT puede aparecer en Beekeeper, pero no para leer una tabla: es la forma de llamar una función que escribe de manera controlada y devuelve la confirmación.

Cómo sería la conexión

  1. El docente obtiene en Supabase → Connect una cadena de conexión de Session pooler, adecuada para una aplicación de escritorio en una red IPv4.
  2. En Beekeeper se crea una conexión PostgreSQL usando ese host, puerto, base de datos, el usuario reserva_escritura, su contraseña y SSL activado. La clave publishable del formulario no sirve aquí: no es una contraseña de PostgreSQL.
  3. Se comprueba la identidad con SELECT current_user;. Debe devolver reserva_escritura, no postgres.
  4. Para registrar, se usa únicamente la puerta permitida:
SELECT * FROM public.registrar_reserva(
  'Ana Pérez', '3001234567', DATE '2026-09-15', TIME '19:00', 2, 3
);

La función aplica las mismas validaciones del formulario y, si todo es válido, crea la reserva. Si no, devuelve el mensaje de rechazo. El rol no puede ejecutar DELETE, UPDATE ni SELECT * FROM reserva.

Por qué no dar INSERT directo

Registrar una reserva puede necesitar crear o reutilizar un cliente, encontrar la mesa por su número y respetar las validaciones. Dar INSERT sobre las tablas obligaría a conceder más permisos y permitiría saltarse esas reglas. La función mantiene el proceso completo, atómico y limitado a una sola acción de negocio.

Este es un patrón de diseño para una herramienta de escritorio confiable. Para los estudiantes y el formulario público, la vía correcta sigue siendo la API con clave publishable, RLS y las tres funciones permitidas.
