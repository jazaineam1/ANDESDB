Problema

Una sola celda mezcla plato y cantidad. El dato está visible, pero no está consultable limpiamente.

Pregunta: ¿cuántos Ajiacos vendimos?

3FNAntes
Dependencia transitiva

El dato llega por un rodeo

pedido_id→mesa_id→puestos

Si sabes el pedido, puedes saber la mesa. Si sabes la mesa, puedes saber los puestos. Entonces puestos vive naturalmente en MESA.

3FNRodeo: pedido → mesa → puestos

Cambia la capacidad en una sola copia

Ahora la mesa 1 puede aparecer con 4 puestos y con 6 puestos. La base permite la contradicción porque el diseño repite el dato.

Puente

¿Qué acabamos de necesitar?

Estructura

No bastaba con consultar mejor. Había que crear tablas, columnas, claves y restricciones.

DDL es SQL para definir estructura: CREATE TABLE, ALTER TABLE, DROP TABLE.
DDLAhora el nombre sí tiene sentido
Anatomía

Lee un CREATE TABLE de arriba hacia abajo

CREATE TABLE plato (
    plato_id INTEGER PRIMARY KEY,
    nombre VARCHAR(80) NOT NULL,
    precio NUMERIC(10,2) NOT NULL CHECK (precio > 0),
    activo BOOLEAN NOT NULL DEFAULT TRUE
);

Tabla

Columna

Tipo

Restricción

CREATE TABLELeer antes de escribir
Tabla 1

Primera tabla: MESA

CREATE TABLE mesa (
    mesa_id INTEGER PRIMARY KEY,
    codigo VARCHAR(10) NOT NULL UNIQUE,
    puestos INTEGER NOT NULL CHECK (puestos > 0),
    activa BOOLEAN NOT NULL DEFAULT TRUE
);
Lectura suave: cada mesa tiene un identificador, un código visible, una capacidad positiva y un estado.
DDLPK · UNIQUE · CHECK · DEFAULT
Tabla 2

Segunda tabla: PLATO

CREATE TABLE plato (
    plato_id INTEGER PRIMARY KEY,
    nombre VARCHAR(80) NOT NULL,
    precio NUMERIC(10,2) NOT NULL CHECK (precio > 0),
    activo BOOLEAN NOT NULL DEFAULT TRUE
);
No inventes restricciones: podríamos hacer nombre UNIQUE, pero solo si el negocio confirma que nunca habrá dos platos con el mismo nombre.
DDLReglas justificadas
Tabla 3

Tercera tabla: PEDIDO

CREATE TABLE pedido (
    pedido_id INTEGER PRIMARY KEY,
    fecha TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    mesa_id INTEGER NOT NULL REFERENCES mesa(mesa_id),
    estado VARCHAR(20) NOT NULL CHECK (estado IN ('abierto','pagado','cancelado'))
);
FK: mesa_id en pedido debe existir antes en mesa.
DDLPedido apunta a mesa
Relación muchos a muchos

La relación N:N se vuelve tabla

CREATE TABLE linea_pedido (
    pedido_id INTEGER NOT NULL REFERENCES pedido(pedido_id),
    plato_id INTEGER NOT NULL REFERENCES plato(plato_id),
    cantidad INTEGER NOT NULL CHECK (cantidad > 0),
    precio_unitario NUMERIC(10,2) NOT NULL CHECK (precio_unitario >= 0),
    PRIMARY KEY (pedido_id, plato_id)
);
cantidad depende de las dos partes: del pedido y del plato.
DDLPK compuesta + dos FK

Reconstrucción final

Separar tablas no significa perder información

SELECT p.pedido_id,
       m.codigo AS mesa,
       pl.nombre AS plato,
       l.cantidad,
       l.precio_unitario,
       l.cantidad * l.precio_unitario AS subtotal
FROM pedido p
JOIN mesa m ON m.mesa_id = p.mesa_id
JOIN linea_pedido l ON l.pedido_id = p.pedido_id
JOIN plato pl ON pl.plato_id = l.plato_id;
Si el JOIN reconstruye la historia, la separación no destruyó el negocio.
JOINReconstrucción sin pérdida
Criterio profesional

No toda restricción se debe imponer

Sí

Precio positivo: CHECK.

Sí

Pedido apunta a mesa existente: FK.

Depende

Nombre de plato único: solo si el negocio lo confirma.

El buen diseño no consiste en poner muchas restricciones; consiste en poner las restricciones correctas.
