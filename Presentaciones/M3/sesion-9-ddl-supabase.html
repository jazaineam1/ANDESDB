Checkpoint 2 · crea pedido

CREATE TABLE pedido (
    pedido_id BIGINT GENERATED ALWAYS AS IDENTITY,
    creado_en TIMESTAMP NOT NULL DEFAULT NOW(),
    estado TEXT NOT NULL DEFAULT 'abierto',
    CONSTRAINT pk_pedido PRIMARY KEY (pedido_id)
);
  1. Ejecuta solo este CREATE TABLE.
  2. Abre Table Editor.
  3. Busca tu schema.
  4. Comprueba que existe pedido con tres columnas.
No sigas si la tabla no aparece. Primero corrige el paso actual.

Checkpoint 4 · crea plato

CREATE TABLE plato (
    plato_id BIGINT GENERATED ALWAYS AS IDENTITY,
    nombre TEXT NOT NULL,
    precio_actual NUMERIC(10,2),
    CONSTRAINT pk_plato PRIMARY KEY (plato_id),
    CONSTRAINT ck_plato_precio
        CHECK (precio_actual IS NULL OR precio_actual >= 0)
);
  1. Ejecuta el bloque.
  2. Verifica la tabla.
  3. Lee el CHECK en español: “si hay precio, no puede ser negativo”.

ANDESDB · Sesión 9Pausa
95–110 min · Tercera tabla

Checkpoint 6 · crea linea_pedido

CREATE TABLE linea_pedido (
    linea_id BIGINT GENERATED ALWAYS AS IDENTITY,
    pedido_id BIGINT NOT NULL,
    plato_id BIGINT NOT NULL,
    cantidad INTEGER NOT NULL,
    precio_unitario NUMERIC(10,2) NOT NULL,
    CONSTRAINT pk_linea_pedido PRIMARY KEY (linea_id),
    CONSTRAINT fk_linea_pedido_pedido
        FOREIGN KEY (pedido_id) REFERENCES pedido(pedido_id),
    CONSTRAINT fk_linea_pedido_plato
        FOREIGN KEY (plato_id) REFERENCES plato(plato_id),
    CONSTRAINT ck_linea_cantidad CHECK (cantidad > 0),
    CONSTRAINT ck_linea_precio CHECK (precio_unitario >= 0)
);

Lectura de la FK: si una línea dice pedido_id = 7, el pedido 7 debe existir en pedido.

ANDESDB · Sesión 9Checkpoint 7
120–136 min · Dos errores distintos

Una FK y un CHECK no fallan por la misma razón

Checkpoint 8 · FK

INSERT INTO linea_pedido
(pedido_id, plato_id, cantidad, precio_unitario)
VALUES (999999, 1, 1, 28000);

Debe fallar por fk_linea_pedido_pedido.

Checkpoint 9 · CHECK

INSERT INTO linea_pedido
(pedido_id, plato_id, cantidad, precio_unitario)
VALUES (1, 1, 0, 28000);

Debe fallar por ck_linea_cantidad.

FK: el valor debe apuntar a algo real. NOT NULL: el valor no puede faltar. CHECK: la fila debe cumplir una condición.

Extensión guiada: cliente, mesa y reserva

El archivo Scripts/S9.sql deja esta parte separada. No la abras si todavía no puedes explicar los errores anteriores.

Recupera una idea clave

R1 sigue candidata: una reserva pendiente puede estar incompleta. Por eso fecha, hora, personas y cliente no se convierten silenciosamente en NOT NULL global.

Representar una relación no significa hacerla obligatoria. FK ≠ NOT NULL.

Cómo sabes que aprendiste

  • Puedes crear tu schema y una tabla.
  • Puedes leer nombre TIPO RESTRICCIÓN.
  • Puedes verificar el efecto en Table Editor.
  • Puedes explicar IDENTITY, PK, FK, NOT NULL, CHECK y DEFAULT.
  • Puedes provocar un error y reconocer qué constraint lo causó.
  • Puedes distinguir regla del negocio de decisión del modelo.
