ANDESDB · Sesión 9Sintaxis de restricciones
18–33 min · Reglas con nombre

¿Para qué usamos CONSTRAINT?

CONSTRAINT pk_cliente
    PRIMARY KEY (cliente_id)

CONSTRAINT fk_reserva_cliente
    FOREIGN KEY (cliente_id)
    REFERENCES cliente(cliente_id)

CONSTRAINT pk_cliente

Le damos un nombre a la regla para reconocerla en el esquema y en los errores.

PRIMARY KEY (...)

Indicamos qué clase de restricción es y sobre qué columna o columnas actúa.

FOREIGN KEY (cliente_id) REFERENCES cliente(cliente_id) se lee: “este valor debe existir como cliente_id en cliente”.

ANDESDB · Sesión 9Sintaxis CONSTRAINT
18–33 min · Anatomía

Primera tabla: cliente

CREATE TABLE cliente (
    cliente_id BIGINT GENERATED ALWAYS AS IDENTITY,
    nombre TEXT NOT NULL,
    telefono TEXT,

    CONSTRAINT pk_cliente PRIMARY KEY (cliente_id),
    CONSTRAINT uq_cliente_telefono UNIQUE (telefono)
);

Lectura natural: cada cliente tiene un identificador generado, un nombre obligatorio y un teléfono que no puede repetirse si se registra.

ANDESDB · Sesión 9Primer CREATE
18–33 min · Distinción crítica

IDENTITY y PRIMARY KEY no son lo mismo

GENERATED ALWAYS AS IDENTITY

Genera números automáticamente.

PRIMARY KEY

Identifica de forma única cada fila.

El número automático ayuda. La clave primaria es la regla de identidad.

ANDESDB · Sesión 9Identity y PK
33–48 min · FK

Segunda tabla: reserva

CREATE TABLE reserva (
    reserva_id BIGINT GENERATED ALWAYS AS IDENTITY,
    cliente_id BIGINT NOT NULL,
    fecha DATE NOT NULL,
    hora TIME NOT NULL,
    personas INTEGER NOT NULL,

    CONSTRAINT pk_reserva PRIMARY KEY (reserva_id),
    CONSTRAINT fk_reserva_cliente
      FOREIGN KEY (cliente_id) REFERENCES cliente(cliente_id),
    CONSTRAINT ck_reserva_personas CHECK (personas > 0)
);

S7 decía: RESERVA pertenece a CLIENTE. S9 lo traduce como FOREIGN KEY.

ANDESDB · Sesión 9Restricciones
33–48 min · No todo cabe ahí

Un CHECK no puede verlo todo

Sí cabe

  • personas > 0
  • precio >= 0
  • estado IN (...)

No cabe como CHECK simple

  • comparar con puestos de otra tabla
  • evitar reservas solapadas complejas
  • validar suma de pagos

Una restricción demasiado débil permite errores; una demasiado fuerte prohíbe negocio válido.

ANDESDB · Sesión 9CHECK tiene límites
48–60 min · SQLite → PostgreSQL

SQL cambia un poco entre motores

NecesidadSQLite/localPostgreSQL/Supabase
identificadorINTEGERBIGINT GENERATED ... AS IDENTITY
textoTEXTTEXT o VARCHAR(n)
dineroREALNUMERIC(10,2)
booleano0/1BOOLEAN
fecha/horaTEXTDATE, TIME, TIMESTAMP
claves foráneasPRAGMA foreign_keys = ON;se borra — en PostgreSQL siempre están activas

Empiecen por esa última. El SQL que trae el constructor arranca con la línea PRAGMA, que en SQLite enciende las claves foráneas y en PostgreSQL no existe: si la pegan, el primer error sale antes de crear una sola tabla. Bórrenla y sigan.

ANDESDB · Sesión 9Romper la base
115–135 min · El payoff

Una frase del negocio se vuelve regla ejecutable

INSERT INTO reserva (cliente_id, fecha, hora, personas)
VALUES (999999, '2026-09-04', '20:00', 4);

Debe fallar: no existe ningún cliente con cliente_id = 999999.

El motor acaba de negarse a guardar un dato porque ustedes convirtieron una frase en estructura.
