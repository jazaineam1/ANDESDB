Primera tabla: pedido

CREATE TABLE pedido (
    pedido_id BIGINT GENERATED ALWAYS AS IDENTITY,
    creado_en TIMESTAMP NOT NULL DEFAULT NOW(),
    estado TEXT NOT NULL DEFAULT 'abierto',
    CONSTRAINT pk_pedido PRIMARY KEY (pedido_id)
);
  1. Copia solo este bloque debajo del SET search_path.
  2. Selecciona el CREATE TABLE.
  3. Presiona Run.
  4. Abre Table Editor y busca tu schema.
  5. Comprueba que exista pedido con tres columnas.
No sigas si no encuentras la tabla. El objetivo no es llegar rápido; es comprobar cada efecto.

ANDESDB · Sesión 9Checkpoint 3
60–70 min · Checkpoint 4

Segunda tabla: plato y un CHECK

CREATE TABLE plato (
    plato_id BIGINT GENERATED ALWAYS AS IDENTITY,
    nombre TEXT NOT NULL,
    precio_actual NUMERIC(10,2),
    CONSTRAINT pk_plato PRIMARY KEY (plato_id),
    CONSTRAINT ck_plato_precio
        CHECK (precio_actual IS NULL OR precio_actual >= 0)
);
  1. Ejecuta el bloque.
  2. Verifica plato en Table Editor.
  3. Lee el CHECK en español: “si hay precio, no puede ser negativo”.

ANDESDB · Sesión 9Pausa
92–105 min · Checkpoint 6

Tercera tabla: linea_pedido

CREATE TABLE linea_pedido (
    linea_id BIGINT GENERATED ALWAYS AS IDENTITY,
    pedido_id BIGINT NOT NULL,
    plato_id BIGINT NOT NULL,
    cantidad INTEGER NOT NULL,
    precio_unitario NUMERIC(10,2) NOT NULL,
    CONSTRAINT pk_linea_pedido PRIMARY KEY (linea_id),
    CONSTRAINT fk_linea_pedido_pedido
        FOREIGN KEY (pedido_id) REFERENCES pedido(pedido_id),
    CONSTRAINT fk_linea_pedido_plato
        FOREIGN KEY (plato_id) REFERENCES plato(plato_id),
    CONSTRAINT ck_linea_cantidad CHECK (cantidad > 0),
    CONSTRAINT ck_linea_precio CHECK (precio_unitario >= 0)
);

Lectura natural de la FK: “si una línea dice pedido_id = 7, el pedido 7 debe existir en pedido”.

115–124 min · Checkpoint 8

Prueba una referencia que no existe

INSERT INTO linea_pedido
    (pedido_id, plato_id, cantidad, precio_unitario)
VALUES
    (999999, 1, 1, 28000);
  1. Ejecuta solo este INSERT.
  2. Debe fallar.
  3. Busca fk_linea_pedido_pedido en el error.
  4. Explica la diferencia entre FK y NOT NULL.

Respuesta: NOT NULL exige que haya un valor. FK exige que, si hay un valor, apunte a una fila real.

Extensión: cliente, mesa y reserva

No empieces esta parte si todavía no entendiste los checkpoints anteriores. El archivo Scripts/S9.sql la deja separada y comentada como extensión.

Qué añade

  • otra PK técnica en cliente;
  • capacidad de mesa;
  • dos FK desde reserva;
  • una reserva pendiente que puede estar incompleta.

Qué enseña

  • R1 sigue siendo candidata.
  • Representar una relación no la hace obligatoria.
  • DDL no convierte “confirmar” en “existir”.

No convertimos fecha, hora, personas y cliente en NOT NULL global. La frase hablaba de confirmar la reserva y todavía no hemos confirmado la política exacta.

ANDESDB · Sesión 9Extensión guiada
153–160 min · Límite del DDL

Que una regla esté confirmada no significa que quepa en un CHECK

ReglaPor qué necesita más contexto
R2 solapescompara intervalos entre varias reservas
R3 capacidadcompara reserva.personas con mesa.puestos
R9 pagossuma varias filas
R10 meserodepende de quién ejecuta la operación

Certeza y capa son ejes diferentes. Una regla puede estar confirmada y aun así necesitar lógica de transacción, base o aplicación.

ANDESDB · Sesión 9Límite del DDL
160–165 min · Salida

La prueba de que aprendiste no es cuánto SQL pegaste

  • Puedes abrir SQL Editor y crear tu schema.
  • Puedes leer nombre TIPO RESTRICCIÓN.
  • Puedes crear una tabla y verificarla en Table Editor.
  • Puedes explicar IDENTITY, PK, FK, NOT NULL, CHECK y DEFAULT.
  • Puedes provocar un error y reconocer qué constraint lo causó.
  • Puedes decir qué parte es regla del negocio y qué parte es decisión del modelo.

Frase final: DDL hace ejecutable una decisión; no fabrica la evidencia que la justifica.
