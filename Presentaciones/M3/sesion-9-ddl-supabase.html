Ahora sí: ¿qué es DDL?

DDL es la parte de SQL con la que definimos o cambiamos la estructura de la base.

Quiero...Uso...Cambia...
leer datosSELECTnada
insertar o actualizar filasINSERT, UPDATE, DELETElos datos
crear tablas y reglasCREATE, ALTER, DROPla estructura
Frase de bolsillo: DML cambia filas; DDL cambia el lugar donde vivirán esas filas.

70–82 minutos · primera tabla real

Crear plato

CREATE TABLE plato (
    plato_id BIGINT GENERATED ALWAYS AS IDENTITY,
    nombre TEXT NOT NULL,
    precio_actual NUMERIC(10,2) NOT NULL,

    CONSTRAINT pk_plato PRIMARY KEY (plato_id),
    CONSTRAINT ck_plato_precio CHECK (precio_actual >= 0)
);
Antes de ejecutar: señala cuál línea identifica la fila, cuál obliga un dato y cuál impide precios negativos.

92–104 minutos · IDENTITY y DEFAULT

Crear pedido

CREATE TABLE pedido (
    pedido_id BIGINT GENERATED ALWAYS AS IDENTITY,
    creado_en TIMESTAMPTZ NOT NULL DEFAULT now(),
    estado TEXT NOT NULL DEFAULT 'abierto',

    CONSTRAINT pk_pedido PRIMARY KEY (pedido_id),
    CONSTRAINT ck_pedido_estado
        CHECK (estado IN ('abierto', 'en cocina', 'cerrado'))
);
Dos ideas distintas: IDENTITY genera números; PRIMARY KEY dice que ese número identifica la fila.

Porque un pedido puede tener varios platos y un plato puede aparecer en muchos pedidos.

120–136 minutos útiles · relación real

Crear linea_pedido

CREATE TABLE linea_pedido (
    linea_id BIGINT GENERATED ALWAYS AS IDENTITY,
    pedido_id BIGINT NOT NULL,
    plato_id BIGINT NOT NULL,
    cantidad INTEGER NOT NULL,
    precio_unitario NUMERIC(10,2) NOT NULL,

    CONSTRAINT pk_linea_pedido PRIMARY KEY (linea_id),
    CONSTRAINT fk_linea_pedido_pedido
        FOREIGN KEY (pedido_id) REFERENCES pedido(pedido_id),
    CONSTRAINT fk_linea_pedido_plato
        FOREIGN KEY (plato_id) REFERENCES plato(plato_id),
    CONSTRAINT ck_linea_cantidad CHECK (cantidad > 0),
    CONSTRAINT ck_linea_precio CHECK (precio_unitario >= 0)
);
Checkpoint 4FK + CHECK
136–144 minutos útiles · lectura natural

Lee la FK en español

FOREIGN KEY (pedido_id)
REFERENCES pedido(pedido_id)

“El pedido_id que escriba en linea_pedido debe existir primero en pedido.”

Una FK no dibuja una flecha bonita. Impide apuntar a algo que no existe.

¿Y la clave compuesta de S8?

Lo que usamos hoy

linea_id como PK técnica.

Es simple para practicar FK, INSERT y errores.

Otra decisión defendible

PRIMARY KEY (pedido_id, plato_id)

Sirve si el negocio decide que un plato solo aparece una vez por pedido y la cantidad acumula unidades.

No es contradicción: una clave sustituta facilita el laboratorio; una clave compuesta expresa otra regla de unicidad. La elección debe justificarse.

DiseñoNo vender una sola respuesta
182–188 minutos útiles · restricción sin inventar reglas

UNIQUE solo si el negocio lo confirma

-- Si el negocio confirma que no puede repetirse:
ALTER TABLE plato
ADD CONSTRAINT uq_plato_nombre UNIQUE (nombre);

No lo agregues porque “suena bonito”. UNIQUE afirma que dos filas no pueden compartir ese valor.

UNIQUERegla fuerte, no decoración

DROP no es “borrar filas”

DROP TABLE linea_pedido;

DELETE borra filas. DROP elimina la tabla.

Orden práctico: para crear, padres antes que hijos; para destruir, hijos antes que padres.

La sesión se logra si puedes explicar cada línea

  • Sabes qué parte del modelo se traduce a tabla, columna, PK, FK y CHECK.
  • Entiendes que DDL cambia estructura; DML cambia filas.
  • Ejecutaste SQL en PostgreSQL sin perderte en Supabase.
  • Provocaste un error de FK, uno de CHECK y uno de NOT NULL.
  • Identificaste qué restricción actuó en el mensaje del motor.
  • Reconociste una regla que no debes imponer sin evidencia, como UNIQUE.

Payoff: una frase del negocio terminó convertida en una regla que el motor puede defender.
