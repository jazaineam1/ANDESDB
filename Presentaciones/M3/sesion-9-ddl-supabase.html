Haz que la propia base confiese la contradicción

SELECT plato_id,
       COUNT(DISTINCT nombre_plato) AS nombres_distintos
FROM lab_2fn_linea_mal
GROUP BY plato_id
HAVING COUNT(DISTINCT nombre_plato) > 1;
Si aparece plato_id = 10, la base afirma dos nombres para el mismo plato.

34–40 minutos · separar y reconstruir

Ejecuta “INCIDENTE 2 · REPARACIÓN”

PEDIDO → fecha_pedido PLATO → nombre_plato PEDIDO+PLATO → cantidad

Ahora cambia el nombre una sola vez en lab_2fn_plato_bien y reconstruye:

SELECT l.pedido_id, p.nombre_plato, l.cantidad
FROM lab_2fn_linea_bien l
JOIN lab_2fn_plato_bien p
  ON p.plato_id = l.plato_id
WHERE l.plato_id = 10;
Todas las filas muestran el mismo nombre.
Nombre técnico: 2FN importa cuando la clave tiene varias partes: un atributo no debería depender solo de una parte de esa clave.

45–50 minutos · la base se contradice

Pregunta a la base cuántas capacidades tiene cada mesa

SELECT mesa_id,
       COUNT(DISTINCT puestos) AS capacidades_distintas
FROM lab_3fn_pedido_mal
GROUP BY mesa_id
HAVING COUNT(DISTINCT puestos) > 1;
Mesa 1 aparece con dos capacidades. El motor no considera esto un error: nosotros diseñamos una estructura que permite la contradicción.
pedido_id → mesa_id → puestos

puestos depende de mesa_id, no directamente del pedido.

DiagnósticoDependencia por un rodeo
50–56 minutos · una sola copia

Ejecuta “INCIDENTE 3 · REPARACIÓN”

La capacidad queda una sola vez en mesa. Los pedidos solo conservan mesa_id.

SELECT p.pedido_id, p.mesa_id, m.puestos
FROM lab_3fn_pedido_bien p
JOIN lab_3fn_mesa_bien m
  ON m.mesa_id = p.mesa_id
WHERE p.mesa_id = 1;
Todos muestran 6 puestos después de un único UPDATE.
Nombre técnico: 3FN evita que un atributo dependa de otra columna no clave que ya está dentro de la tabla.

86–98 minutos · primera tabla consciente

Ahora sí: crea plato

CREATE TABLE plato (
    plato_id BIGINT GENERATED ALWAYS AS IDENTITY,
    nombre TEXT NOT NULL,
    precio_actual NUMERIC(10,2) NOT NULL,

    CONSTRAINT pk_plato PRIMARY KEY (plato_id),
    CONSTRAINT ck_plato_precio CHECK (precio_actual >= 0)
);
Antes de ejecutar: señala la línea que identifica la fila, la que obliga el nombre y la que rechaza precios negativos.
Dos cosas distintas: IDENTITY genera el número; PRIMARY KEY lo declara identificador de la fila.

CREATE TABLE pedido (
    pedido_id BIGINT GENERATED ALWAYS AS IDENTITY,
    creado_en TIMESTAMPTZ NOT NULL DEFAULT now(),

¿Por qué necesitamos linea_pedido?

Pedido

Puede contener muchos platos.

Plato

Puede aparecer en muchos pedidos.

N:N → entidad asociativa. Además, cantidad y precio_unitario describen “este plato en este pedido”.

122–136 minutos útiles · relación real

Crear linea_pedido

CREATE TABLE linea_pedido (
    linea_id BIGINT GENERATED ALWAYS AS IDENTITY,
    pedido_id BIGINT NOT NULL,
    plato_id BIGINT NOT NULL,
    cantidad INTEGER NOT NULL,
    precio_unitario NUMERIC(10,2) NOT NULL,

    CONSTRAINT pk_linea_pedido PRIMARY KEY (linea_id),
    CONSTRAINT fk_linea_pedido_pedido
        FOREIGN KEY (pedido_id) REFERENCES pedido(pedido_id),
    CONSTRAINT fk_linea_pedido_plato
        FOREIGN KEY (plato_id) REFERENCES plato(plato_id),
    CONSTRAINT ck_linea_cantidad CHECK (cantidad > 0),
    CONSTRAINT ck_linea_precio CHECK (precio_unitario >= 0)
);

157–162 minutos útiles · diseño responsable

Que PostgreSQL pueda imponerlo no significa que debamos imponerlo

¿PK compuesta / UNIQUE?

UNIQUE(pedido_id, plato_id) solo si el negocio prohíbe repetir el mismo plato en líneas separadas.

¿Nombre único?

UNIQUE(nombre) solo si dos platos no pueden compartir nombre.

DDL hace ejecutable una decisión. No convierte una suposición en una regla verdadera.

  • 2FN: usaste COUNT(DISTINCT) y HAVING para descubrir una dependencia de media clave.
