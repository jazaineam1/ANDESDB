Dos mundos

“Clave” no siempre significa lo mismo

Modelo de datos

PRIMARY KEY identifica filas. FOREIGN KEY conecta tablas.

Ejemplo: pedido_id, plato_id.

Plataforma Supabase

API keys y contraseñas permiten conectar aplicaciones o herramientas.

No son columnas de tus tablas.

DDL 1

Primera tabla: MESA

CREATE TABLE mesa (
    mesa_id INTEGER PRIMARY KEY,
    codigo VARCHAR(20) NOT NULL UNIQUE,
    puestos INTEGER NOT NULL CHECK (puestos > 0),
    activa BOOLEAN NOT NULL DEFAULT TRUE
);
PK: mesa_id identifica la mesa. CHECK: puestos debe ser positivo.
Crear MESAANDESDB · Sesión 9
DDL 2

Segunda tabla: PLATO

CREATE TABLE plato (
    plato_id INTEGER PRIMARY KEY,
    nombre VARCHAR(80) NOT NULL UNIQUE,
    precio NUMERIC(10,2) NOT NULL CHECK (precio > 0),
    activo BOOLEAN NOT NULL DEFAULT TRUE
);
UNIQUE: úsalo solo si el negocio decide que no habrá dos platos con el mismo nombre.
Crear PLATOANDESDB · Sesión 9
DDL 3

Tercera tabla: PEDIDO

CREATE TABLE pedido (
    pedido_id INTEGER PRIMARY KEY,
    fecha TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    mesa_id INTEGER NOT NULL,
    estado VARCHAR(20) NOT NULL DEFAULT 'abierto',
    FOREIGN KEY (mesa_id) REFERENCES mesa(mesa_id),
    CHECK (estado IN ('abierto','pagado','cancelado'))
);
La FK impide pedidos con mesas inexistentes.
Crear PEDIDOANDESDB · Sesión 9
DDL 4

La relación N:N se vuelve tabla

CREATE TABLE linea_pedido (
    pedido_id INTEGER NOT NULL,
    plato_id INTEGER NOT NULL,
    cantidad INTEGER NOT NULL CHECK (cantidad > 0),
    precio_unitario NUMERIC(10,2) NOT NULL CHECK (precio_unitario > 0),
    PRIMARY KEY (pedido_id, plato_id),
    FOREIGN KEY (pedido_id) REFERENCES pedido(pedido_id),
    FOREIGN KEY (plato_id) REFERENCES plato(plato_id)
);
La PK compuesta dice: en un pedido, un mismo plato aparece una sola vez como línea.

Pruebas que deben fallar

Cada error tiene una razón

-- FK: mesa inexistente
INSERT INTO pedido (pedido_id, mesa_id) VALUES (101, 999);

-- CHECK: cantidad inválida
INSERT INTO linea_pedido (pedido_id, plato_id, cantidad, precio_unitario)
VALUES (100, 10, 0, 18000);

-- NOT NULL: nombre obligatorio
INSERT INTO plato (plato_id, nombre, precio) VALUES (11, NULL, 15000);
ErrorQué enseña
FKNo apuntar a inexistentes.
CHECKNo toda cantidad vale.
NOT NULLUn obligatorio no puede faltar.

Consultar después de normalizar

Separar tablas no significa perder información

SELECT pe.pedido_id,
       pe.fecha,
       m.codigo AS mesa,
       p.nombre AS plato,
       l.cantidad,
       l.precio_unitario,
       l.cantidad * l.precio_unitario AS subtotal
FROM pedido pe
JOIN mesa m ON m.mesa_id = pe.mesa_id
JOIN linea_pedido l ON l.pedido_id = pe.pedido_id
JOIN plato p ON p.plato_id = l.plato_id;
Guardamos separado; leemos junto con JOIN.

Diseño responsable

No toda restricción se debe imponer

Sí imponer

  • precio > 0
  • cantidad > 0
  • mesa existente
  • estado permitido

No inventar

  • cliente único por pedido si no se dijo
  • precio inmutable si no se dijo
  • nombre único si negocio no lo exige
