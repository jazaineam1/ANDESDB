Fíjate en dos cosas antes de empezar

Cuatro preguntas para saber que funciona

Pégalas en el SQL Editor, una por una, y pulsa Run. No sirven solo para comprobar: cada una enseña por qué el modelo está hecho así.

El total que no se guarda

PEDIDO no tiene columna total, a propósito. Se reconstruye sumando las líneas. Compáralo con la tabla PAGO: el pedido 4 se pagó en dos veces, 90.000 + 94.000 = 184.000, que es justo lo que da esta consulta.

SELECT p.pedido_id,
       SUM(l.cantidad * l.precio_unitario) AS total
FROM pedido p
JOIN linea_pedido l ON l.pedido_id = p.pedido_id
GROUP BY p.pedido_id
ORDER BY p.pedido_id;

El precio de ayer no es el de hoy

El ajiaco vale hoy 28.000 y en los pedidos viejos aparece a 26.000. Las dos cifras son correctas porque son datos distintos: uno es el precio de la carta y el otro el de aquella cuenta. Es la única copia que el modelo guarda queriendo.

SELECT l.linea_id,
       pl.nombre,
       l.precio_unitario AS precio_de_aquel_dia,
       pl.precio_actual  AS precio_de_hoy
FROM linea_pedido l
JOIN plato pl ON pl.plato_id = l.plato_id
WHERE pl.nombre = 'Ajiaco santafereño';

El plato que nadie ha pedido

El tamal está en la carta y no aparece en ninguna línea de pedido. Existe igual, porque PLATO es su propia tabla y no depende de que alguien lo pida. En una base mal hecha, un plato no existiría hasta la primera venta.

SELECT pl.nombre,
       COUNT(l.linea_id) AS veces_pedido
FROM plato pl
LEFT JOIN linea_pedido l ON l.plato_id = pl.plato_id
GROUP BY pl.nombre
ORDER BY veces_pedido;

La fiesta que ocupó dos mesas

El pedido 4 se sentó en la mesa 3 y en la mesa 4. Sin la tabla puente pedido_mesa esto no se podría ni escribir: habría que elegir una de las dos mesas y mentir.

SELECT pm.pedido_id,
       m.numero AS mesa,
       m.puestos
FROM pedido_mesa pm
JOIN mesa m ON m.mesa_id = pm.mesa_id
WHERE pm.pedido_id = 4;

Si algo sale mal

Los mensajes de PostgreSQL dicen exactamente qué pasó, pero en inglés y de golpe. Estos son los seis que vas a ver.

Lo que diceLo que significa
relation "cliente" does not existEl guión no se ejecutó, o se ejecutó solo un trozo. Vuelve al SQL Editor, selecciona todo con Ctrl + A y pulsa Run.
Success. No rows returnedNo es un error. CREATE e INSERT cambian la base pero no devuelven una tabla de resultados. Compruébalo en Table Editor.
duplicate key value violates unique constraintEstás insertando algo que ya existe —dos mesas con el mismo número, dos meseros con la misma cédula—. La base te está defendiendo.
violates foreign key constraintEstás apuntando a una fila que no existe: una reserva del cliente 999 cuando solo hay ocho clientes. Mira primero qué identificadores hay de verdad.
violates check constraintEl valor no cumple la regla que le pusimos: puestos mayor que cero, personas mayor que cero, estado entre los tres permitidos.
null value in column ... violates not-null constraintFalta un dato obligatorio. Un plato sin nombre no es un plato.

Y el remedio universal

Vuelve a ejecutar el guión entero. Empieza borrando lo que hubiera, así que siempre te deja en un estado limpio y conocido.

Por qué el formulario puede usar una clave publishable

Una clave publishable identifica a una página pública; no es una contraseña ni debe usarse para administrar PostgreSQL. La seguridad real está en las reglas de la base: RLS mantiene las tablas cerradas y el formulario solo puede llamar a mesas_disponibles(), registrar_reserva() y listar_reservas().

Nunca compartas: la contraseña de la base, una cadena de conexión directa ni una clave secret. Esas sí tienen privilegios elevados y no pertenecen a un navegador.

Listo para volver al taller

Ya no estás imaginando una tabla: creaste una base real y viste una regla aplicarse cuando una página intentó guardar una reserva. Ahora sí tiene sentido decidir qué datos deberían seguir siendo relacionales y cuáles no.

Qué regla aplica cada base

No todas las reglas se pueden expresar con el mismo mecanismo. Identificarlas evita prometer una protección que el modelo todavía no tiene.

En tu guion de once tablas

  • PRIMARY KEY identifica cada fila.
  • FOREIGN KEY impide referencias a clientes, mesas o pedidos inexistentes.
  • CHECK exige valores válidos, como personas > 0.
  • UNIQUE (mesa_id, fecha, hora) impide la reserva exactamente igual de una mesa en la misma fecha y hora.

Límite consciente: como el modelo solo guarda hora, no puede detectar intervalos que se traslapan. Y comparar personas con mesa.puestos requiere mirar otra tabla; no cabe en un CHECK simple.

En el formulario compartido

  • La función registrar_reserva() consulta la mesa y decide disponibilidad y capacidad.
  • RLS mantiene las tablas cerradas: el navegador no recibe permiso para insertar filas directamente.
  • Las funciones son la puerta limitada para leer mesas, registrar la reserva y listarla.

Conclusión: una restricción de columna no reemplaza una regla que depende de varias filas o tablas.

Consultas de negocio para explorar tu base

Estas preguntas no crean ni modifican datos. Ejecuta cada SELECT en el SQL Editor después de cargar las once tablas. Antes de pulsar Run, predice el nivel de detalle y después explica qué decisión apoyaría el resultado.

1. ¿Qué platos generan más ingresos?

Una fila por plato. Compara volumen vendido con dinero recaudado; el precio de la línea es el precio histórico cobrado.

SELECT pl.nombre,
       SUM(l.cantidad) AS unidades_vendidas,
       SUM(l.cantidad * l.precio_unitario) AS ingresos
FROM linea_pedido AS l
JOIN plato AS pl ON pl.plato_id = l.plato_id
GROUP BY pl.plato_id, pl.nombre
ORDER BY ingresos DESC;
Interpretación: un plato puede vender muchas unidades y no ser el primero en ingresos. Si no hay filas, revisa que existan líneas de pedido.

2. ¿Cuáles son los pedidos de mayor valor?

Reconstruye el total desde el detalle para que una copia guardada no quede desactualizada.

SELECT p.pedido_id,
       p.estado,
       SUM(l.cantidad * l.precio_unitario) AS total_reconstruido
FROM pedido AS p
JOIN linea_pedido AS l ON l.pedido_id = p.pedido_id
GROUP BY p.pedido_id, p.estado
ORDER BY total_reconstruido DESC
LIMIT 3;
Interpretación: el JOIN interno muestra pedidos con detalle. Para encontrar pedidos vacíos, usa la consulta siguiente.

3. ¿Hay pedidos creados sin líneas?

Un pedido vacío puede ser un borrador legítimo o un fallo del flujo de caja. Primero hazlo visible.

SELECT p.pedido_id,
       p.estado
FROM pedido AS p
LEFT JOIN linea_pedido AS l ON l.pedido_id = p.pedido_id
WHERE l.linea_id IS NULL
ORDER BY p.pedido_id;
Interpretación: cero filas significa que todos tienen al menos una línea. Una o más filas piden revisar la aplicación, no borrar a ciegas.

4. ¿Qué líneas tienen valores imposibles?

Es una auditoría independiente de las restricciones: sirve para comprobar que los datos existentes respetan el modelo.

SELECT COUNT(*) AS lineas_invalidas
FROM linea_pedido
WHERE cantidad <= 0
   OR precio_unitario < 0;
Interpretación: el resultado esperado es 0. Si aparece otro número, detén la carga y revisa qué proceso permitió ese valor.
