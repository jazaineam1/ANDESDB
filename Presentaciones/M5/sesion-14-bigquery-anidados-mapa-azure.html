El mismo pedido puede representarse de tres formas

Relacional

pedido + linea_pedido. Separar ayuda cuando las partes cambian y se validan de forma independiente.

Documento

Las líneas pueden viajar embebidas si normalmente se leen y cambian junto con el pedido.

Analítico anidado

BigQuery puede conservar la jerarquía dentro de una fila mediante ARRAY y STRUCT.

Pregunta: ¿cambió el negocio o cambió la carga de trabajo que queremos optimizar?
PuenteModelo ↔ patrón de acceso
Decisión de diseño

Normalizar y anidar no son doctrinas opuestas

Operación

Si una línea se crea, modifica o valida por separado, una tabla independiente protege reglas y evita redundancia operacional.

Analítica

Si casi siempre analizas el pedido con todas sus líneas, anidar puede acercar la forma del dato a la consulta y evitar JOINs repetidos.

Regla mental: primero pregunta cómo se lee y cómo cambia el dato; después decide si separar o anidar.
DiseñoCarga de trabajo antes que dogma
Antes de mirar sintaxis

¿Qué dato queremos representar?

pedido_idplatocantidad
42Ajiaco2
42Jugo1

Forma plana

Dos filas repiten pedido_id = 42. Cada fila representa una línea del pedido.

Forma anidada

Pedido 42 │ ├── Ajiaco × 2 └── Jugo × 1

Queremos conservar el pedido completo como una sola fila que contiene sus líneas.

Pregunta guía: ¿cómo guardamos varias líneas dentro de una fila sin convertirlas en texto?
CasoPrimero el dato, luego el SQL
Entrada → construcción

STRUCT agrupa campos; ARRAY conserva varios elementos

SELECT STRUCT(
  42 AS pedido_id,
  [STRUCT('Ajiaco' AS plato, 2 AS cantidad),
   STRUCT('Jugo'   AS plato, 1 AS cantidad)] AS lineas
) AS pedido;

Importante: aquí no entra una tabla

La consulta construye el dato directamente con valores escritos en el SQL. El SELECT crea una fila.

Qué estamos construyendo

pedido ← STRUCT exterior ├── pedido_id = 42 └── lineas ← ARRAY ├── STRUCT {plato:Ajiaco, cantidad:2} └── STRUCT {plato:Jugo, cantidad:1}
BigQueryConstruir jerarquía explícita
Construcción → salida

¿Qué sale realmente de esa consulta?

pedido
{pedido_id: 42, lineas: [{Ajiaco, 2}, {Jugo, 1}]}

Resultado

FILA 1 pedido ├── pedido_id: 42 └── lineas: ├── [0] Ajiaco · 2 └── [1] Jugo · 1

Respuesta a la predicción

Devuelve 1 fila.

Dentro de esa fila existen 2 líneas.

lineas es un ARRAY<STRUCT<...>>: una lista cuyos elementos tienen campos.

Idea clave: una fila puede contener varios elementos sin dejar de ser una sola fila.
Resultado1 fila · 2 elementos internos
Antes de expandir

El WITH crea exactamente esta entrada

WITH pedidos AS (
  SELECT 42 AS pedido_id,
    [STRUCT('Ajiaco' AS plato, 2 AS cantidad),
     STRUCT('Jugo'   AS plato, 1 AS cantidad)] AS lineas
)
SELECT * FROM pedidos;
pedido_idlineas
42[{Ajiaco,2}, {Jugo,1}]
Grano antes de UNNEST: una fila representa un pedido completo. Las dos líneas siguen dentro de esa misma fila.
UNNESTPrimero declara el grano de entrada
Entrada → operación → salida

UNNEST(lineas) convierte cada elemento del ARRAY en una fila

SELECT pedido_id, l.plato, l.cantidad
FROM pedidos,
UNNEST(lineas) AS l;
1 fila
pedido 42 + ARRAY de 2 líneas
→ UNNEST →
2 filas
una por cada elemento
pedido_idplatocantidad
42Ajiaco2
42Jugo1

¿Qué es l?

Es el alias de cada elemento del arreglo. Por eso podemos pedir l.plato y l.cantidad.

Nuevo grano

Antes: 1 fila = 1 pedido.
Después: 1 fila = 1 línea del pedido.

UNNESTExpandir también cambia el grano
El peligro conocido · paso 1

Una fila puede contener dos arreglos independientes

WITH pedidos AS (
  SELECT 42 AS pedido_id,
    [STRUCT('Ajiaco' AS plato,2 AS cantidad),
     STRUCT('Jugo'   AS plato,1 AS cantidad),
     STRUCT('Postre' AS plato,1 AS cantidad)] AS lineas,
    ['DESCUENTO10','CLIENTEVIP'] AS promociones
)

ARRAY 1 · líneas

Ajiaco × 2 Jugo × 1 Postre × 1

3 elementos

ARRAY 2 · promociones

DESCUENTO10 CLIENTEVIP

2 elementos

La fila sigue representando un pedido. Aún no hemos expandido ninguno de los dos arreglos.
Doble UNNEST3 líneas + 2 promociones
El peligro conocido · paso 2

Si expandes ambos sin relación, obtienes todas las combinaciones

SELECT pedido_id, l.plato, l.cantidad, p AS promocion
FROM pedidos
CROSS JOIN UNNEST(lineas) AS l
CROSS JOIN UNNEST(promociones) AS p;
3 líneas × 2 promociones = 6 filas
pedido_idplatocantidadpromocion
42Ajiaco2DESCUENTO10
42Ajiaco2CLIENTEVIP
42Jugo1DESCUENTO10
42Jugo1CLIENTEVIP
42Postre1DESCUENTO10
42Postre1CLIENTEVIP
BigQuery no está “equivocado”: pedimos expandir dos colecciones independientes. Sin una relación adicional, cada línea queda combinada con cada promoción.
Doble UNNESTProducto de combinaciones
Por qué importa

Multiplicar filas puede cambiar tus métricas sin que notes el error

Dato original

Ajiaco 2 Jugo 1 Postre 1

Total real = 4

Después del doble UNNEST

Ajiaco 2 Ajiaco 2 Jugo 1 Jugo 1 Postre 1 Postre 1

SUM(cantidad) = 8

El problema es de grano, no de sintaxis. El SQL ejecutó exactamente lo pedido, pero duplicamos cada línea al combinarla con dos promociones.
Antes de cada UNNEST preguntaEn este ejemplo
¿Qué representa una fila ahora?Un pedido
¿Cuántos elementos estoy expandiendo?3 líneas; luego 2 promociones
¿Qué representará una fila después?Primero una línea; luego una combinación línea × promoción
Regla: UNNEST puede cambiar conteos, sumas y promedios. Después de expandir, vuelve a declarar: “una fila representa…”.
Reasoning CheckGrano antes que agregación
Transferencia · mismo pedido

CSV, JSON y Parquet pueden representar el mismo negocio de formas distintas

CSV · plano

pedido_id,plato,cantidad
42,Ajiaco,2
42,Jugo,1

La jerarquía se aplana y pedido_id se repite.

JSON · jerárquico

{
 "pedido_id":42,
 "lineas":[
  {"plato":"Ajiaco","cantidad":2},
  {"plato":"Jugo","cantidad":1}
 ]
}

Parquet · analítico tipado

pedido_id: INT64 lineas: ARRAY<STRUCT< plato STRING, cantidad INT64 >>

Puede conservar estructura, pero no está pensado para leerlo a mano.

Conexión: objeto JSON se parece mentalmente a STRUCT y arreglo JSON a ARRAY; la equivalencia es conceptual, no literal.
FormatosMismo dato · distinta representación física
Formato 1

CSV · intercambio tabular simple y universal

Qué es

Texto organizado en filas y columnas separadas por delimitadores. Funciona muy bien cuando el dato ya tiene forma de tabla.

Fortalezas

Fácil de inspeccionar, compartir y abrir. Prácticamente cualquier herramienta de datos lo entiende.

Dónde lo ves

ExcelGoogle SheetspandasRPower BIBigQueryERP / CRM

Cuándo elegirlo

Exportaciones, intercambio entre personas/sistemas y datasets tabulares pequeños o medianos.

Limitación: no representa de forma natural objetos, listas o estructuras jerárquicas; normalmente debes aplanarlas.

¿Qué hizo realmente BigQuery?

ARRAY

Permitió varios elementos asociados a una misma fila.

STRUCT

Agrupó campos relacionados sin convertirlos en columnas independientes al mismo nivel.

UNNEST

Expandió una colección y cambió explícitamente el grano del resultado.

Salida

La sesión cabe en cuatro decisiones

  • ARRAY: varios elementos permanecen asociados a una fila.
  • STRUCT: varios campos relacionados permanecen agrupados.
  • UNNEST: expandir un arreglo cambia el grano y puede multiplicar métricas si expandes colecciones independientes.
  • Formato/servicio: CSV, JSON, Parquet, Blob o Cosmos se eligen por uso, no por moda.
