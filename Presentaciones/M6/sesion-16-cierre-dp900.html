Diseño de bases de datos

Pasaste de una conversación de negocio a un modelo defendible

regla→entidad→atributo→relación→cardinalidad

Identidad

PK identifica una fila. Una clave no es “porque sí”: representa identidad estable.

Relaciones

FK conecta entidades y protege referencias. 1:1, 1:N y N:N cambian el diseño.

Dependencias

Separar atributos por dependencia reduce redundancia y anomalías.

reglas → ER → claves → cardinalidad → 1FN/2FN/3FN → esquema implementable
Microcaso: “un pedido tiene muchas líneas y cada línea pertenece a un pedido”. ¿Qué cardinalidad ves y dónde quedaría la FK?

De operación a analítica

La misma empresa necesita estructuras distintas para operar y analizar

OLTP · operar ahora

Muchas operaciones pequeñas, integridad, estado actual y baja latencia.

pedido · cliente · reserva · transacción

OLAP · entender historia

Lecturas amplias, agregaciones, comparaciones y decisiones sobre periodos; el modelo estrella organiza hechos y dimensiones.

hecho + dimensiones + medidas + tiempo

Modelo estrella

Una tabla de hechos en un grano definido se relaciona con dimensiones descriptivas.

Batch

Procesa lotes acumulados.

Streaming

Procesa eventos conforme llegan.

Data warehouseestrella + grano + carga
Analítica cloud

No solo escribiste SQL: aprendiste que leer datos también cuesta

Partición

Recorta bloques por una clave —frecuentemente fecha— para evitar leer datos innecesarios.

Clustering

Organiza por columnas consultadas con frecuencia dentro de la tabla/partición.

Pruning

El motor evita bloques que no pueden satisfacer el filtro.

misma respuesta lógica ≠ mismo costo físico

La decisión física nace del patrón de consultas: filtros frecuentes, volumen, distribución y bytes procesados.

Predicción: si casi todas las consultas filtran por fecha, ¿qué columna candidata a partición revisarías primero y por qué?

Datos semiestructurados

También cambiaste la forma de representar una fila

JSON / ARRAY / STRUCT

Un registro puede contener objetos y listas. La estructura existe, pero no tiene que ser una tabla plana.

pedido.items[] → ARRAY de STRUCT

UNNEST

Expande un arreglo a filas. La pregunta obligatoria es: ¿qué representa una fila antes y después?

FROM pedidos p CROSS JOIN UNNEST(p.items) i
CSV

Tabular simple.

JSON

Jerarquía flexible.

Parquet

Columnar, eficiente para analítica.

Antes de UNNEST: un pedido tiene 4 ítems. ¿Cuántas filas esperas después de expandir solo ese arreglo? ¿Qué representa cada fila?
