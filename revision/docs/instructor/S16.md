# S16 · Guía docente

## Pregunta central
¿Qué aprendí, cómo se traduce al lenguaje del DP-900 y qué debo hacer —con fecha— antes de que venza mi voucher?

## Hilo conductor
- **Hereda:** S1 planteó las cinco preguntas de línea base, pero esas respuestas no necesariamente quedaron persistidas; S15 mostró desempeño integrador sin receta.
- **Primero cierra el curso:** reconstruye S1 → S15 antes de hablar de certificación. Si no hay respuestas S1 guardadas, la comparación es reflexión retrospectiva, no medición.
- **Después abre el examen:** explica experiencia, blueprint, modalidad, idioma, Practice Assessment, Exam Sandbox y programación.
- **Diagnóstico:** 24 escenarios en proporción 7–6–4–7, cercana a los rangos oficiales del blueprint.
- **Clasificación:** cada error se clasifica como C/T/L: concepto, transferencia o lectura.
- **Exploración real:** abrir en clase Study Guide, Practice Assessment, Exam Sandbox y página de programación.
- **Evidencia de salida:** resultado por dominio + C/T/L + dominio prioritario + fecha objetivo + vencimiento del voucher.

## Presupuesto docente · 180 minutos totales = 165 útiles + 15 de pausa
- **0–10 · Apertura honesta:** “hoy no abrimos un tema nuevo del curso”; nombra las tres dudas: SQL, guía y vocabulario.
- **10–35 · Devolución S15:** tres patrones de alto valor + traducción Arena/Mutation/Boss + 5 minutos de repetición en práctica guiada.
- **35–50 · Todo el SQL que escribiste:** S2–S15 + mapa diseñar → implementar → consultar → decidir dónde guardar.
- **50–60 · Reflexión S1:** cinco respuestas actuales. Si no existe línea base guardada, no lo llames medición pre/post.
- **60–75 · Pausa:** 15 minutos.
- **75–93 · Cómo funciona DP-900:** 45 min de examen, 65 de seat duration, 700 escalado, cantidad variable, modalidad, idioma/accommodations y voucher.
- **93–103 · Cápsula Azure + certificaciones:** Azure SQL / open source administrado + Blob / Files / Table / Cosmos DB + rutas de certificación.
- **103–148 · Diagnóstico:** 24 ítems 7–6–4–7, confianza previa y C/T/L. **45 minutos**: no lo reduzcas si mantienes formatos mixtos.
- **148–162 · Exploración oficial:** Study Guide + 5 preguntas del Practice Assessment + Exam Sandbox + página de programación.
- **162–177 · Plan + portafolio:** fecha objetivo antes del voucher, dominio prioritario, evidencias para CV/GitHub y glosario.
- **177–180 · Encuesta + cierre:** pide honestidad, no una buena calificación de satisfacción.

El minutaje es guía docente. **No se proyecta minuto por minuto en cada diapositiva**: la presentación mantiene la política de pacing del repositorio y solo muestra la pausa.


## Devolución S15
Antes de clase abre **`s15-analytics.html`**. Ese panel puede mostrar *misconceptions* y checkpoints de S15 v7 cuando existen envíos registrados. Si hay una muestra suficiente, toma los **tres misconceptions con mayor frecuencia** y construye la devolución con esos datos.

Si el panel está vacío o la muestra es insuficiente, **no inventes “los tres más frecuentes”**. Usa el trío pedagógico preparado en el deck: último evento vs. fila con ese estado, restricciones por comportamiento y mezcla de granos. En la auditoría del 19-sep-2026, la vista `s15_attempt_analytics_v5` reportó **0 intentos y 0 estudiantes**, así que no había base para un ranking de errores. **Vuelve a revisar el panel antes de clase**: si ya hay intentos, usa los datos reales; si no, aplica el fallback.

Traduce además el vocabulario del Workbench: **SQL Arena = depurar consultas con casos borde; DDL Mutation = contrastar un esquema correcto con uno defectuoso; Boss Transfer = aplicar el razonamiento en un caso nuevo**.

Después de S16, abre **/ANDESDB/s16-analytics.html** para ver resultados por dominio, C/T/L, confianza, voucher, portafolio y encuesta. Ese panel usa el resumen enviado por cada estudiante y no expone las 24 respuestas individuales.

## “Todo el SQL que escribiste”
No lo presentes como defensa del curso; úsalo como evidencia acumulada:
- S2–S3: SELECT / WHERE / GROUP BY / HAVING.
- S4: LEFT JOIN + ausencia.
- S5: CTE + COUNT(DISTINCT).
- S6: consultas para demostrar reglas con evidencia.
- S9: CREATE TABLE + PK/FK/CHECK en PostgreSQL real.
- S12: consultas sobre modelo estrella.
- S13: GoogleSQL para partición y clustering físico.
- S14: CROSS JOIN UNNEST.
- S15: integración de todo lo anterior.

Después dibuja el mapa: **diseñar → implementar → consultar → decidir dónde guardar**. Explica que “Diseño y gestión” es más amplio que sintaxis SQL y que Big Data apareció cuando cambiaron volumen, formato, grano, distribución y costo de lectura.

## Cápsula de vocabulario DP-900
El curso cubrió gran parte del razonamiento, no todos los nombres Azure. En 10–12 minutos, fija solo estas diferencias:
- Azure SQL Database: base PaaS.
- Managed Instance: PaaS con alta compatibilidad de instancia.
- SQL Server on Azure VM: control de VM/SO.
- Azure Database for PostgreSQL/MySQL: motores open source administrados.
- Blob: objetos; Files: archivo compartido; Table: clave/atributo; Cosmos DB: NoSQL distribuido.

La frase docente es **“nombre nuevo, concepto parcialmente conocido”**, no “esto debieron saberlo”.

## Error esperable principal
Convertir DP-900 en una lista de productos Azure o, en el extremo contrario, asumir que el curso ya cubrió de manera explícita todo el vocabulario de servicios. La sesión debe separar con claridad: concepto trabajado, nombre Azure nuevo y preparación específica del examen.

## Dónde probablemente se atascan
- Al confundir 45 minutos de examen con 65 minutos de seat duration.
- Al interpretar 700 como “70 % correcto”; es una puntuación escalada.
- Al responder por palabra clave: “JSON → Cosmos”, “Spark → cualquier analítica”, “SQL Server → cualquier Azure SQL”.
- Al distinguir Azure SQL Database, Managed Instance y SQL Server on Azure VM.
- Al distinguir Blob, Files, Table y Cosmos DB por requisito.
- Al distinguir Databricks, Fabric y Power BI por etapa de la carga.
- Al clasificar un error como C/T/L sin justificar la causa.
- Al construir un plan sin fecha de voucher ni fecha objetivo.

## Notas de precisión sobre DP-900
- Mantén **45 minutos de examen** y **65 minutos de seat duration**. No uses “60 minutos”.
- No prometas un número exacto de preguntas. Microsoft indica que el número puede variar; por eso la diapositiva dice **Variable**.
- Si el examen no está disponible en el idioma preferido, el tiempo adicional por idioma se solicita mediante accommodation **antes de agendar** y puede requerir documentación.
- El Practice Assessment ayuda a practicar estilo y retroalimentación, pero Microsoft aclara que no representa necesariamente longitud ni complejidad del examen real.

## No avanzar hasta que…
Antes del diagnóstico, el grupo debe poder explicar:
1. que DP-900 es un examen Fundamentals de 45 minutos de examen;
2. que 700 es una puntuación escalada;
3. que los pesos vigentes son 25–30 / 20–25 / 15–20 / 25–30;
4. que la cantidad de preguntas puede variar y no debe enseñarse como una cifra garantizada;
5. que el examen puede programarse normalmente online o en centro según disponibilidad.

Durante el diagnóstico, no avances al plan hasta que cada estudiante haya identificado al menos un error C/T/L y pueda explicar una elección con la cadena:
**requisito → carga → forma del dato → familia → servicio**.

## Cobertura del reporte docente
El botón **Enviar diagnóstico al docente** usa `learning-track` y requiere una sesión LMS válida. En modo invitado el resultado queda guardado localmente y **no aparece en `s16-analytics.html`**.

Antes de S16:
- verifica cuántos estudiantes tienen acceso real al portal;
- si quieres analítica completa de la cohorte, asegúrate de que entren autenticados antes de enviar;
- no interpretes “enviaron X de Y” como tasa de participación de toda la clase si parte del grupo trabajó como invitado.

No abras un endpoint anónimo para resolver esta diferencia: sería fácil de falsificar y mezclaría resultados sin identidad verificable.

## Si vas 15 minutos atrasado
No recortes la explicación operativa del examen ni el plan con fecha. Reduce la discusión plenaria del diagnóstico: deja que el estudiante responda las 24 preguntas y comenta solo los distractores con mayor tasa de error. En la exploración oficial, abre al menos Study Guide + 5 preguntas del Practice Assessment + Exam Sandbox.

## Si vas 15 minutos adelantado
- Cambia una condición crítica de un escenario y pregunta si cambia el servicio.
- Compara Azure SQL Database vs Managed Instance vs VM con un mismo caso.
- Compara Blob vs Files vs Table vs Cosmos con una misma forma de dato pero diferente patrón de acceso.
- Pide que un estudiante transforme un error T en una explicación de servicio sin mirar opciones.
- Ejecuta más preguntas del Practice Assessment oficial.

## Intervención docente
No respondas con el nombre del servicio antes de reconstruir el escenario:
1. ¿Qué pide realmente?
2. ¿Qué carga es?
3. ¿Qué forma y patrón de acceso tienen los datos?
4. ¿Qué familia satisface esas condiciones?
5. Solo entonces, ¿qué nombre usa Azure?

Para C/T/L:
- **C:** el estudiante no podría resolverlo aunque quitaras los nombres Microsoft.
- **T:** entiende el concepto, pero no reconoce el equivalente Azure.
- **L:** conoce concepto y servicio, pero ignoró una condición escrita.

En preguntas de servicio, exige explicar por qué el distractor más cercano **no** aplica.

## Regla de cierre
Nadie termina S16 con “voy a estudiar DP-900”. Termina con:
**dominio prioritario + tipo de error dominante + recurso oficial + fecha objetivo + voucher**.

Si aún no conocen la fecha de expiración del voucher, la primera acción del plan es confirmarla. No inventes una ventana fija de 2–3 semanas sin esa información.
