S6 · calidad y evidencia

0 · Diagnóstico de datos imperfectos

Esta estación no da puntos. Retoma la idea de S6: separar lo que los datos sí muestran de una suposición sobre la causa.

Duplicados de caso

SELECT caso_id, COUNT(*) AS filas
FROM casos_dirty
GROUP BY caso_id
HAVING COUNT(*) > 1;
Por qué: agrupar por identificador y pedir conteos mayores a 1 revela IDs repetidos.

NULL en tipo

SELECT *
FROM casos_dirty
WHERE tipo IS NULL;

Eventos cuyo caso no existe

SELECT e.*
FROM eventos_dirty e
LEFT JOIN casos_dirty c
  ON c.caso_id = e.caso_id
WHERE c.caso_id IS NULL;
Clasificación correcta: “Existe un evento cuyo caso no aparece en CASOS” = lo muestran los datos. “Ocurrió por una falla de sincronización” = es una suposición que los datos no demuestran.
S2–S5 · SQL y nivel de agregación

1 · SQL Arena

Estas consultas priorizan claridad. Antes de cada una pregunta: ¿qué debe representar una fila del resultado?

Q1 · Casos de prioridad Alta por barrio

SELECT barrio,
       COUNT(*) AS casos_alta
FROM casos_src
WHERE prioridad = 'Alta'
GROUP BY barrio;
Por qué: primero filtras exactamente la población “Alta” y después cuentas dentro de cada barrio.

Q2 · Último evento temporal

WITH ultima_fecha AS (
  SELECT caso_id,
         MAX(fecha_evento) AS fecha_evento
  FROM eventos_src
  GROUP BY caso_id
)
SELECT c.caso_id,
       c.estado AS estado_actual,
       e.estado AS ultimo_estado
FROM casos_src c
LEFT JOIN ultima_fecha u
  ON u.caso_id = c.caso_id
LEFT JOIN eventos_src e
  ON e.caso_id = u.caso_id
 AND e.fecha_evento = u.fecha_evento;
Por qué: MAX(estado) ordena texto; no busca el último estado en el tiempo. Primero encuentras la fecha más reciente y luego recuperas el estado de esa fila.

Q3 · Minutos acumulados de casos cuyo último evento es Cerrado

WITH ultima_fecha AS (
  SELECT caso_id,
         MAX(fecha_evento) AS fecha_evento
  FROM eventos_src
  GROUP BY caso_id
),
cerrados AS (
  SELECT u.caso_id
  FROM ultima_fecha u
  JOIN eventos_src e
    ON e.caso_id = u.caso_id
   AND e.fecha_evento = u.fecha_evento
  WHERE e.estado = 'Cerrado'
)
SELECT e.caso_id,
       SUM(e.minutos_desde_anterior) AS minutos_hasta_cierre
FROM eventos_src e
JOIN cerrados c
  ON c.caso_id = e.caso_id
GROUP BY e.caso_id;
Por qué: primero decides qué casos terminan cerrados. Después vuelves a todo su historial y sumas la trayectoria completa. Un caso que se cerró y luego se reabrió no entra.

Q4 · Totales sin inflar por un JOIN 1:N

SELECT COUNT(DISTINCT c.caso_id) AS total_casos,
       COUNT(e.evento_id) AS total_eventos,
       COUNT(DISTINCT CASE
         WHEN c.prioridad = 'Alta' THEN c.caso_id
       END) AS casos_alta
FROM casos_src c
LEFT JOIN eventos_src e
  ON e.caso_id = c.caso_id;
Por qué: un JOIN 1:N puede repetir una entidad. COUNT(DISTINCT c.caso_id) protege el conteo de casos, COUNT(e.evento_id) cuenta eventos y CASE limita el tercer conteo a prioridad Alta.

Q5 · Promedio de minutos por caso y tipo

WITH por_caso AS (
  SELECT c.caso_id,
         c.tipo,
         COALESCE(SUM(e.minutos_desde_anterior), 0) AS total_minutos
  FROM casos_src c
  LEFT JOIN eventos_src e
    ON e.caso_id = c.caso_id
  GROUP BY c.caso_id, c.tipo
)
SELECT tipo,
       COUNT(*) AS casos,
       ROUND(AVG(total_minutos), 1) AS promedio_minutos
FROM por_caso
GROUP BY tipo;
Por qué: primero vuelves a una fila por caso. Luego promedias casos, no eventos. COALESCE(...,0) hace que un caso sin eventos aporte 0 minutos.

S9 · integridad

3 · DDL y restricciones

Una versión mínima y suficiente es:

CREATE TABLE caso(
  caso_id INTEGER PRIMARY KEY,
  fecha_creacion TEXT NOT NULL,
  tipo TEXT NOT NULL,
  prioridad TEXT NOT NULL,
  estado TEXT NOT NULL,
  barrio TEXT NOT NULL
);

CREATE TABLE evento(
  evento_id TEXT PRIMARY KEY,
  caso_id INTEGER NOT NULL,
  fecha_evento TEXT NOT NULL,
  estado TEXT NOT NULL,
  minutos_desde_anterior INTEGER NOT NULL
    CHECK (minutos_desde_anterior >= 0),
  FOREIGN KEY (caso_id) REFERENCES caso(caso_id)
);
Por qué: PK rechaza duplicados; FK rechaza huérfanos; NOT NULL protege campos obligatorios; CHECK acepta 0 pero rechaza negativos.

Cómo comprobar las reglas con lo visto en S9

En S9 se trabajó una idea suficiente para esta parte: una restricción debe aceptar lo válido y rechazar lo inválido. Por eso puedes comprobar tu DDL con INSERT sencillos.

PRIMARY KEY · un ID repetido debe fallar
INSERT INTO caso(
  caso_id, fecha_creacion, tipo, prioridad, estado, barrio
)
VALUES (
  9001, '2026-09-02', 'Ruido', 'Alta', 'Abierto', 'Prueba'
);

Si ya existe caso_id=9001, la PRIMARY KEY debe impedir otra fila con el mismo identificador.

FOREIGN KEY · un caso inexistente debe fallar
INSERT INTO evento(
  evento_id, caso_id, fecha_evento, estado, minutos_desde_anterior
)
VALUES (
  9200, 9999, '2026-09-01 09:00', 'Abierto', 0
);

Si caso_id=9999 no existe, la FOREIGN KEY debe impedir el INSERT.

CHECK · cero debe pasar y un negativo debe fallar
-- debe pasar
INSERT INTO evento(
  evento_id, caso_id, fecha_evento, estado, minutos_desde_anterior
)
VALUES (9201, 9001, '2026-09-01 10:00', 'Abierto', 0);

-- debe fallar
INSERT INTO evento(
  evento_id, caso_id, fecha_evento, estado, minutos_desde_anterior
)
VALUES (9202, 9001, '2026-09-01 10:10', 'Abierto', -1);

Es exactamente la lógica de S9: prueba un dato permitido y otro que viola la regla.

S13 · diseño físico

6 · BigQuery: partición y clustering

PARTITION BY: fecha_evento
CLUSTER BY: barrio, tipo — en ese orden.
Por qué: 100% de las consultas acota fecha; 82% filtra barrio; 54% de esas también usa tipo. En S13 la decisión se toma a partir del patrón de consulta. Como caso_id no aparece en esos filtros, no debe desplazar columnas que sí se usan.

Una representación conceptual del diseño sería:

PARTITION BY DATE(fecha_evento)
CLUSTER BY barrio, tipo

La sintaxis exacta depende de cómo esté declarada fecha_evento en la tabla. Lo evaluado en el Workbench es la decisión física.

UNNEST mínimo

SELECT c.caso_id,
       ev.tipo
FROM `proyecto.dataset.casos_nested` AS c
CROSS JOIN UNNEST(c.evidencias) AS ev;
Por qué: antes del UNNEST una fila representa un caso; después, una fila representa una evidencia del caso. Se conserva caso_id para no perder la identidad del registro padre.

Resumen

La lógica que conviene recordar

SQL: define la población y el nivel de agregación antes de contar. Modelo: entidades, relaciones, cardinalidad y dependencias. DDL: una restricción debe aceptar lo válido y rechazar lo inválido. Documentos: embeber o referenciar depende del patrón de acceso y del ciclo de vida. Data warehouse: grano antes que medidas. BigQuery: partición y clustering se deciden desde el patrón de consulta. UNNEST: explica qué representa una fila antes y después. Azure: primero la necesidad y después la familia de servicio.

Si puedes explicar esas ocho ideas sin mirar el código, el solucionario ya cumplió su propósito.
